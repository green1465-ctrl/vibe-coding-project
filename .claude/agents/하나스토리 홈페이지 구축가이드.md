# 홈페이지 구축 가이드 (하나스토리 프로젝트 기반)

> 이 문서 쓰는 법: 새 프로젝트 폴더에서 "`~/.claude/agents/홈페이지구축가이드.md` 참고해서 [사이트이름] 회사소개 홈페이지 만들어줘"라고 던지면 됨. 아래 체크리스트 답만 다르게 주면 나머지 패턴(구조·인증·배포)은 그대로 재사용 가능.

---

## 0. 이 가이드가 맞는 상황

이런 사이트에 맞음:
- 회사소개형 정적 사이트(홈/회사소개/제품/인증/실적/문의 등 5~10페이지)
- 고객사(관리자)가 **직접 텍스트·이미지를 수정**할 수 있어야 함 → 그래서 관리자 CMS 필요
- 회원가입/결제 등 복잡한 기능은 없고, **관리자 1명(또는 소수) 로그인**만 있으면 됨
- 트래픽이 아주 크지 않음 (중소기업 사이트 수준)

이 가이드가 안 맞는 상황: 회원 다수 가입/로그인, 실시간 기능, 대용량 트래픽 예상 — 이런 경우는 처음부터 구조를 다르게 잡아야 함(이 문서 범위 밖).

---

## 1. 공통 용어집 (기획·디자인·개발 통일 언어)

같은 개념을 역할마다 다른 말로 부르면 대화가 어긋남. 성찬님과 저는 아래 **왼쪽(통일 용어)**만 쓰기로 함 — 오른쪽은 참고용 동의어일 뿐, 실제 대화·문서에선 안 씀.

| 통일 용어 | 뜻 | 주로 나오는 시점 | 동의어(안 씀, 참고만) |
|---|---|---|---|
| **콘텐츠 구조** | 사이트에 들어갈 텍스트·이미지를 어떤 키-값 형태로 담을지의 설계도 (`content.json`) | 기획 | 데이터 구조, 스키마, 필드 설계 |
| **화면** | 손님이 보는 HTML 페이지 한 장 | 기획·디자인 | 뷰, 스크린, 페이지, 레이아웃 |
| **관리자 CMS** | 고객사가 직접 콘텐츠를 수정하는 화면(`admin.html`) | 기획·개발 공통 | 어드민, 대시보드, 백오피스 |
| **라우트** | 특정 URL 요청을 서버가 처리하는 코드 한 조각 (`/api/content` 등) | 개발 | 엔드포인트, API, 핸들러 |
| **인증** | 로그인해서 관리자 권한을 확인하는 절차(JWT) | 개발 | 로그인, 세션, 토큰 |
| **배포** | 실제 인터넷 주소로 올려서 손님이 접속 가능하게 만드는 것 | 개발 | 호스팅, 런칭, 퍼블리시 |
| **무료 한도** | 돈 안 내고 쓸 수 있는 사용량 상한선 | 기획(비용 논의) | 프리티어, free tier, 무료 티어 |
| **콘텐츠 주입** | 화면의 빈 자리에 콘텐츠 구조 값을 채워 넣는 동작 (`content-loader.js`) | 디자인·개발 | 렌더링, 바인딩, 데이터 바인딩 |

새 용어가 생기면 이 표에 한 줄 추가 — 표가 늘어나는 것 자체가 "우리 둘만의 사전"이 쌓이는 것.

## 2. 표준 아키텍처

```
손님 브라우저 → 화면(HTML/CSS/JS, 빌드 도구 없음)
                     ↓ fetch('/api/content')
              서버(Express or Workers) → DB(콘텐츠 구조 통째로 1행)
                     ↓ (관리자만) POST /api/content, /admin/login
              이미지 업로드 → 외부 이미지 호스팅(ImageKit 등)
```

- 프론트는 **빌드 도구 없는 순수 HTML/CSS/JS**로 충분 (React 필요 없음 — 화면 수가 많지 않고 SEO 상 정적 HTML이 유리).
- 서버는 "정적 파일 서빙 + `/api/*`, `/admin/*` 몇 개 라우트"뿐 — 무겁지 않음.

---

## 3. 역할별 체크리스트 — 담당 에이전트

기획·디자인·개발은 실제로는 저(Claude) 혼자 모자만 바꿔 쓰는 거지만, 역할을 나눠서 부르면 그때그때 어떤 관점으로 답해야 하는지 명확해짐. 아래 세 에이전트는 **이 가이드 전용으로 새로 만든 것**(`~/.claude/agents/`, 전역) — 기존에 있던 `app-mission-architect`/`single-react-dev`/`single-server-specialist`는 각자 다른 용도(일반 앱 기획, React SPA 프로토타입, 인메모리 미니 서버)로 만들어진 것이라 이 홈페이지+CMS 패턴이랑 규칙이 맞지 않아서 그대로 뒀고, 대신 아래 세 개를 새로 만들었음.

### 🧭 기획자 — `@homepage-planner`
- [ ] 사이트 목적·타겟 고객 한 줄 정의
- [ ] 화면 목록 확정 (몇 개, 어떤 이름)
- [ ] **콘텐츠 구조** 설계 — 화면별 텍스트·이미지 항목 나열
- [ ] 관리자가 직접 수정할 항목 vs 개발자만 고치는 항목 구분
- [ ] **인증**이 필요한 사람 수 (관리자 1명인지, 여러 명인지)
- [ ] 상업적 이용 여부 → **배포**(7번) 플랫폼 선택에 영향
- [ ] 예상 방문자 규모 → **무료 한도** 넘는지 대략 가늠
- [ ] 산출물: `PLAN.md`

### 🎨 디자이너/프론트 — `@homepage-frontend-builder`
- [ ] 톤앤매너·레퍼런스 사이트 1~2개
- [ ] 색상·폰트 기본값
- [ ] **화면**별 와이어프레임 또는 설명
- [ ] 모바일 반응형 필요 여부
- [ ] 각 **화면**이 **콘텐츠 구조**의 어떤 키를 쓰는지 매핑 (**콘텐츠 주입** 패턴)
- [ ] 이미지 자리마다 실제 크기·비율 정하기 (업로드 시 깨짐 방지)
- [ ] 순수 HTML/CSS/JS, 여러 화면 — React/SPA 아님

### 🛠 개발자 — `@homepage-cms-backend`
- [ ] 서버 프레임워크 결정 (Express vs Workers) — 7번 섹션 표 참고
- [ ] DB 스키마 (대부분 콘텐츠 구조 통째로 1행)
- [ ] **인증**(JWT) 구현 — 5번 섹션 코드
- [ ] 이미지 업로드 구현 — 6번 섹션 패턴
- [ ] `.env` 분리 + `.env.example`
- [ ] **배포** + 환경변수 등록
- [ ] 검증: 관리자 로그인 → 수정 → DB 반영 → **화면** 정상 로드 확인

> 진행 순서: `@homepage-planner`(PLAN.md 작성) → `@homepage-frontend-builder`(화면) → `@homepage-cms-backend`(서버). 소규모 사이트에서 매번 에이전트를 다 부르는 게 번거로우면, 이 체크리스트만 순서대로 훑고 저한테 그냥 자연스럽게 말해도 됨 — 체크리스트가 "빠뜨린 것 없는지" 확인용 역할을 함.

## 4. 콘텐츠 구조 설계 원칙

**"콘텐츠 구조 = 한 덩어리 JSON"으로 시작 — 과설계 금지.**

관리자가 하는 일이 "텍스트 몇 개, 섹션 몇 개 수정"뿐이라면 화면별/섹션별로 테이블을 쪼개지 말고, `content.json` 하나(또는 DB의 단일 행)에 전체를 넣는다.

```json
{
  "company": { "name": "...", "logo_header": "...", ... },
  "home": { "hero_title": "...", ... },
  "about": { "history": [...], "org": [...] },
  "products": { ... },
  "contact": { ... }
}
```

- **콘텐츠 주입** 패턴(`content-loader.js`): 각 화면 HTML에 `data-content="about.history.0.title"`처럼 dot-notation을 박아두고, 로더 스크립트 하나가 `GET /api/content` 결과를 순회하며 값을 채워넣음. 화면이 늘어나도 로더 코드는 그대로.
- **관리자 CMS**(`admin.html`)는 이 **콘텐츠 구조**를 그대로 반영한 탭(홈페이지/회사소개/제품소개/…)으로 구성. **UI를 매번 새로 설계하지 말고, JSON 키 = 탭/섹션 구조**로 1:1 매핑하면 설계 시간이 크게 줄어듦.
- "전체 읽기 / 전체 덮어쓰기"만 하는 구조라 DB도 정규화된 여러 테이블이 필요 없음 — Postgres면 `JSONB` 컬럼 하나, SQLite/D1이면 `TEXT` 컬럼 하나로 충분.

## 5. 인증(JWT) 표준 패턴 — 관리자 1명, 회원가입 없음

- DB에 유저 테이블 안 만들고, 비밀번호는 환경변수(`ADMIN_PW`)로 관리.
- 로그인 성공 시 JWT 1개 발급(`role:'admin'`, 24h 만료) → `httpOnly` 쿠키(`hs_admin`)에 저장.
- 이후 모든 `/api/content` POST, `/admin/*` 요청은 미들웨어/헬퍼에서 쿠키의 토큰을 검증.

```js
// Express(Node) 버전
const jwt = require('jsonwebtoken');
const token = jwt.sign({ role: 'admin' }, process.env.JWT_SECRET, { expiresIn: '24h' });
res.cookie('hs_admin', token, { httpOnly: true, sameSite: 'lax', secure: process.env.NODE_ENV === 'production' });
```

- 쿠키 옵션은 로컬 http에서도 깨지지 않게 `secure`는 프로덕션에서만 true.
- 비밀번호는 하드코딩 금지, `.env`(로컬)/`.env.example`(더미, 커밋용)/배포 플랫폼 환경변수 3곳에 동일 키로 등록.

## 6. 이미지 업로드 표준 패턴

- 서버 파일시스템에 저장하지 않는다(서버리스는 파일시스템이 휘발성). **외부 이미지 호스팅(ImageKit 등)**에 업로드하고 URL만 DB/JSON에 저장.
- Node/Express: `multer({ storage: multer.memoryStorage() })`로 버퍼 받아서 ImageKit SDK/REST로 업로드.
- 이미지킷 자격증명이 아직 없으면(고객사가 계정 만들기 전) 코드는 미리 짜두되, 환경변수가 비어있을 때 "이미지킷 설정 필요" 같은 명확한 에러만 반환하도록 처리 — 나중에 키만 채우면 바로 동작.

## 7. 배포 플랫폼 선택 기준

| | Vercel | Cloudflare (Pages+Functions+D1) |
|---|---|---|
| 무료 플랜 상업적 이용 | **❌ 금지** (Hobby 플랜 약관) | ✅ 허용 |
| 서버 코드 방식 | Node.js/Express 그대로 (`server.js`) | Workers 런타임 — 파일 기반 라우팅, `req/res` 대신 `Request/Response`, Node 전용 패키지(jsonwebtoken/multer/pg/cookie-parser) 다 재작성 필요 |
| DB | 외부 Postgres(Supabase 등) 붙이기 쉬움 | D1(SQLite) — 행(row) 읽기/쓰기 단위 과금 |
| 배운 커리큘럼과의 궁합 | 3~4주차 Express/pg 그대로 적용 가능 → **처음 만들 때는 이쪽이 빠름** | 학습 곡선 있음. 상업 이용 확정되면 이쪽으로 이전 |
| 결론 | **일단 만들 때 / 회원가입 없는 사내·개인 프로젝트** | **실제 고객사에 납품하는 상업용 사이트**는 처음부터 이쪽 고려, 또는 Vercel Pro($20/월) 결제 |

> 하나스토리는 실제로 Vercel(Express+Supabase)로 먼저 만들고, 상업적 이용 때문에 나중에 Cloudflare로 통째로 이전했음. **다음 프로젝트가 "고객사에 파는 상업용"이라는 게 처음부터 확실하면, Vercel로 갔다가 이전하는 이중 작업 없이 Cloudflare로 바로 시작하는 걸 권장.**

## 8. 실제 진행 순서 (하나스토리에서 밟은 단계, 역할 태그 포함)

1. 🧭 **기획**: 화면 목록 확정 → 콘텐츠 구조 설계(섹션별 키) → 데모 데이터 채워서 구조 확정.
2. 🎨 **화면 제작**: `index.html` 등 + 콘텐츠 주입(`content-loader.js`) 구조 세팅.
3. 🎨 **관리자 CMS 제작**: `admin.html` — 콘텐츠 구조와 1:1 매핑된 탭 UI.
4. 🛠 **서버 구축**: `GET/POST /api/content`, `/admin/login`(JWT), `/api/upload`(이미지).
5. 🛠 **DB 연결**: (Vercel 경로) Supabase 프로젝트 생성 → "Enable Data API" 체크 해제(supabase-js 락인 방지, PostgreSQL만 빌려 씀) → Connect → Drizzle URL 복사 → `.env`에 반영.
6. 🛠 **`.env` 분리**: `DATABASE_URL`, `JWT_SECRET`, `ADMIN_PW`, 이미지킷 키 3종 → `.env`(gitignore) + `.env.example`(더미, 커밋).
7. 🛠 **배포**: Vercel CLI 로그인 → 배포 + 환경변수 등록 → 도메인 확인.
8. 🧭🛠 **검증**: 관리자 로그인 → 텍스트 수정·저장 → DB(Supabase Table Editor 등)에서 실제 반영 확인 → 화면 정상 로드 확인.
9. 🛠 **(상업 이용 확정 시)** Cloudflare 이전: 폴더 통째로 복사 → 서버 코드/설정 파일만 Workers 방식으로 재작성(7번 항목 표 참고) → D1 생성·시딩 → Pages 배포.

## 9. 자주 겪는 문제 (미리 알아두면 시간 절약)

- **Vercel Hobby 플랜은 상업적 이용 금지** — 계약/납품 사이트면 처음부터 확인.
- **서버리스 DB 연결**: Postgres는 반드시 pgbouncer(6543, transaction 모드) 연결 문자열 사용 — direct(5432)는 서버리스에서 커넥션 고갈 위험.
- **Cloudflare Hyperdrive로 기존 Postgres 그대로 이어붙이기**: 로컬 개발(`wrangler pages dev`) 시뮬레이터에서 연결 실패가 잦음 — 안 되면 DB 자체를 D1로 바꾸는 게 더 빠를 수 있음.
- **JWT 라이브러리**: Node 전용(`jsonwebtoken`)과 Workers용(`@tsndr/cloudflare-worker-jwt`)은 API가 다름(후자는 sign/verify가 전부 비동기) — 플랫폼 정할 때 같이 결정.
- **D1 과금 함정**: 반복문 안에서 DB 조회하면 행(row) 수로 과금돼서 요금이 튈 수 있음 — 콘텐츠 구조가 1행뿐이면 이 문제 자체가 거의 없음.
